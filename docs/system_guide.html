Overview

Rally-Racing is a PyBullet driving environment trained with Proximal Policy Optimization (PPO). A car learns to pass a sequence of checkpoints while avoiding obstacles and handling ramps. The project supports two observation regimes:

  • Privileged observation — the policy receives the ground-truth position of the nearest obstacle directly from the simulator.

  • Vision observation — a convolutional network (ObstacleCNN) infers obstacle presence and location from the car’s camera, and those predictions replace the privileged obstacle channels. A privileged policy is fine-tuned into a vision policy.

Training follows a curriculum of increasingly difficult scenarios, and the whole system can be operated either from the command line (manual operation) or through the Tkinter control panel (GUI operation). Both are described in Section 3.

The Curriculum

The scenarios build on one another. Each privileged policy warm-starts from the previous scenario’s privileged policy.

Scenario Track contents
phase1 6 checkpoints, no obstacles, no ramps
phase2 6 checkpoints + 4 obstacles
phase3 6 checkpoints + 4 obstacles + 2 ramps
custom bespoke checkpoint / obstacle / ramp lists

Warm-start chain: phase1→phase2→phase3→custom\text{phase1} \rightarrow \text{phase2} \rightarrow \text{phase3} \rightarrow \text{custom}. A vision policy for a given scenario warm-starts from that scenario’s privileged policy, not from a previous vision policy.

Operation

GUI operation (recommended)

The control panel (src/control.py) exposes every setting and runs every pipeline stage without touching source code. Launch it by double-clicking the Rally-Racing Control Panel icon (after running install_desktop.sh once), or from a terminal:

./launch.sh

The panel is organised into a settings area (left) and a run area (right):

  • Training tab — total timesteps, parallel environments, scenario, PPO hyperparameters, and Weights & Biases logging.

  • Reward weights tab — every coefficient in RewardConfig (Section 4.2), editable live.

  • Vision tab — dataset collection size, CNN training settings, and vision fine-tune budget.

  • Evaluation tab — scenarios to evaluate, episode count, whether to open the simulator window, and the model file to load.

  • Run & Console tab — run any stage individually, or tick several and run them in succession; live output streams to the console.

  • Training Metrics tab — live plots of episode reward, loss, and other scalars read from the local TensorBoard logs, plus an Open in W&B button for the full online dashboard.

Settings are saved to gui_config.json, which the training scripts read at runtime. Nothing is hardcoded in two places.

Manual operation (command line)

Every stage is also a standalone CLI script. The GUI is a convenience layer over exactly these commands; the scripts remain fully usable on their own.

Privileged training.

python3 src/train.py --scenario phase1
python3 src/train.py --scenario phase3 --timesteps 150000 --no-wandb
python3 src/train.py --scenario phase3 --fresh   # ignore warm-start chain

Vision fine-tune

(requires the matching privileged model):

python3 src/train_vision.py --scenario phase3
python3 src/train_vision.py --scenario phase3 --timesteps 200000

Evaluation

(omit –no-render to watch in a window):

python3 src/test.py --model gen2_models/phase3/privileged/best/best_model.zip \
    --scenarios phase3 --episodes 20 --no-render
python3 src/test_vision.py --ppo gen2_models/phase3/vision/best/best_model.zip \
    --scenarios phase3 --episodes 20 --no-render

Relationship between the two.

A GUI “Run” button builds and launches the corresponding command above as a subprocess, passing your saved settings via gui_config.json and command-line arguments. Manual and GUI operation therefore produce identical runs; the GUI simply removes the need to remember flags and paths.

Architecture and Key Functions

This section documents the important functions across the package, grouped by module.

Environment: simple_driving/envs/rally_driving_env.py

RallyDrivingEnv.reset(seed, options)

Re-initialises an episode: respawns the car at the scenario’s start pose, rebuilds the checkpoint list, and (for phase2/phase3) spawns obstacles and ramps. Returns the initial observation. The random seed makes obstacle placement reproducible.

RallyDrivingEnv.step(action)

Advances the simulation by one control step. It applies the action, steps PyBullet, computes the reward through the injected reward_callback, checks termination, and returns the tuple (obs,reward,done,truncated,info)(\text{obs}, \text{reward}, \text{done}, \text{truncated}, \text{info}). If no reward callback was supplied it raises, by design — the environment never silently scores episodes with a default reward.

RallyDrivingEnv.getExtendedObservation()

Builds the 11-dimensional observation vector the policy consumes: [gx,gy,crem,ox,oy,bobs,θpitch,θroll,v,cosψ,sinψ][\, g_x,\ g_y,\ c_{\text{rem}},\ o_x,\ o_y,\ b_{\text{obs}},\ \theta_{\text{pitch}},\ \theta_{\text{roll}},\ v,\ \cos\psi,\ \sin\psi \,] where (gx,gy)(g_x,g_y) is the next checkpoint in the car’s local frame, cremc_{\text{rem}} is the fraction of checkpoints remaining, (ox,oy)(o_x,o_y) is the nearest obstacle in the local frame, bobsb_{\text{obs}} is a 0/10/1 flag for whether an obstacle exists, θpitch\theta_{\text{pitch}} and θroll\theta_{\text{roll}} are chassis angles, vv is planar speed, and (cosψ,sinψ)(\cos\psi,\sin\psi) encodes heading without a wrap discontinuity. Transforming the goal and obstacle into the car’s local frame makes the policy translation- and rotation-invariant.

RallyDrivingEnv.get_camera_image(width, height)

Renders the car’s onboard camera view. Purely additive: it does not affect step, reset, or the reward, so it can be used for vision data collection without altering training dynamics.

RallyDrivingEnv._nearest_obstacle(car_pos)

Returns the closest obstacle and its distance, used both for the observation and for the close-contact reward term.

Reward: src/reward.py

RewardConfig

A dataclass-like container of every reward coefficient (goal reward, obstacle penalty, progress scale, smoothness penalties, repulsive-field parameters, airborne bonus). The GUI edits these values; the environment never hardcodes them.

RewardCalculator.__call__(…)

Computes the scalar reward for one step. The total is a sum of independent terms: r=rprog+rreg+rgoal+rsmooth+rcoll+rrep+roob+rairr = r_{\text{prog}} + r_{\text{reg}} + r_{\text{goal}} + r_{\text{smooth}} + r_{\text{coll}} + r_{\text{rep}} + r_{\text{oob}} + r_{\text{air}} where each term contributes as follows:

  • Progress rprog=rstep+kprogΔdr_{\text{prog}} = r_{\text{step}} + k_{\text{prog}}\,\Delta d, a constant per-step cost plus a bonus proportional to the reduction in distance to the goal Δd\Delta d.

  • Regression rreg=rregr_{\text{reg}} = r_{\text{reg}} when Δd<0\Delta d < 0, an extra penalty for moving away from the goal. It fires in all scenarios (including phase1) so the agent always pays for zigzagging.

  • Checkpoint rgoalr_{\text{goal}} added once when a checkpoint is reached.

  • Smoothness / stability rsmooth=kyaw|jψ|+kroll|Δθr|+kpitch|Δθp|r_{\text{smooth}} = k_{\text{yaw}}\,|j_\psi| + k_{\text{roll}}\,|\Delta\theta_r| + k_{\text{pitch}}\,|\Delta\theta_p|, penalising yaw jerk jψj_\psi (the change in yaw rate) and roll / pitch changes between steps.

  • Collision rcollr_{\text{coll}} applied when the nearest obstacle is within the minimum safe distance.

  • Repulsive field rrep=−krep∑imax(0,R−di)r_{\text{rep}} = -k_{\text{rep}} \sum_i \max(0,\ R - d_i), a soft penalty that grows as the car approaches any obstacle within radius RR, discouraging skimming even without a collision.

  • Boundary roobr_{\text{oob}} applied when the car leaves the world bounds.

  • Airborne rairr_{\text{air}}, a small phase3 bonus for being pitched up while still making forward progress (rewarding committed ramp jumps).

RewardCalculator._wrap_delta(delta)

Wraps an angular difference into [−π,π][-\pi, \pi] so heading changes near the ±π\pm\pi boundary are measured correctly rather than as near-full rotations.

custom_reward(**kwargs)

Module-level functional wrapper around a default RewardCalculator, used as the environment’s reward_callback.

Vision: vision/model.py

ObstacleCNN.forward(x)

Runs the convolutional stack over a camera frame and returns the raw network outputs (logits / regressed coordinates) describing whether an obstacle is visible and where.

ObstacleCNN.predict(x)

Inference wrapper around forward that converts raw outputs into the obstacle-presence flag and local position estimate the vision environment substitutes into the observation vector.

Vision environment: simple_driving/envs/vision_rally_env.py

VisionRallyDrivingEnv.getExtendedObservation()

Overrides the privileged observation: it captures a camera frame, runs the CNN, and replaces the obstacle channels the obstacle channels (ox,oy,bobs)(o_x, o_y, b_{\text{obs}}) with the network’s prediction while leaving all other channels identical. This is what lets a privileged-trained policy be fine-tuned to drive from vision with minimal architectural change.

Training: src/train.py

warm_start_path(scenario)

Returns the path of the policy a new run should warm-start from, encoding the curriculum chain. Returns None when training should start from scratch (e.g. phase1).

make_train_env(scenario, n_envs) / make_eval_env(scenario, log_dir)

Construct the vectorised training environments and the monitored evaluation environment, respectively, wiring in the reward callback and scenario configuration.

make_callbacks(eval_env, best_dir, log_dir, use_wandb, n_envs)

Assembles the Stable-Baselines3 callbacks: periodic evaluation with best-model saving, and (optionally) the Weights & Biases callback. The best-by-evaluation snapshot is what evaluation later loads.

main()

Orchestrates a training run: parse arguments, build environments, load or create the PPO model, attach callbacks and logging, train for the requested timesteps, and save the final model. When W&B is enabled it also records the run URL to logs/<run>/wandb_url.txt so the GUI can open the exact run.

Evaluation: src/test.py

evaluate(model_path, scenarios, render, episodes)

Loads a saved policy and runs it for the requested number of episodes per scenario, reporting per-episode reward, step count, and checkpoint completion. With render=True it opens a PyBullet window so the car can be watched; with render=False it runs headless for fast batch evaluation.

Logging and Metrics

Training writes TensorBoard scalar logs to logs/<gen>_<scenario>_<observation>/. Because training initialises W&B with sync_tensorboard=True, those same scalars also sync to the configured W&B project when logging is enabled. The GUI’s Training Metrics tab reads the local event files directly (no W&B login required) and plots them live; the Open in W&B button jumps to the online run when a URL was recorded.

Known Behaviour

  • Phase3 privileged policy is roughly 90% reliable. Over many episodes most are clean laps, with occasional catastrophic failures in awkward ramp or obstacle configurations.

  • Phase1 evaluation is deterministic. With no obstacles and a fixed spawn, a deterministic policy produces identical episodes — identical eval rewards are expected, not a bug.

  • Vision policies score somewhat below privileged. The CNN-derived observation is noisier than ground truth. A large gap suggests the CNN is not engaging; check the vision_active percentage reported by test_vision.py.
